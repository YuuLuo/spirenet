# SpireHost fidelity ledger (h5-4p)

Game: `sts2.dll` v0.113.1 (commit d09d48e5), SHA256 `62ecbe91093e1fa862de4329aac865209dcb297804caf0f0520d92d8c0b4a9c3`,
verified at every start (`SpireHost.Core\Boot\GameAssemblies.cs`); the file on disk is never modified and no Cecil / IL
rewriting of the game assembly is done. The compile-time reference `host\publicized\sts2.dll` (same assembly with every
member's accessibility flag set to public) is never loaded at run time. The third-party assemblies the resolver
refuses by name (`GameAssemblies.Forbidden`) are not present in `host\game` and the resolver throws if anything asks
for them. The host performs no network IO (rows `metrics-*`, `time-server-request-blocked`). Not a row,
because the host does nothing to it: the Sentry.Godot module initializer of `sts2.dll` runs when the assembly is first
touched, before any patch exists, and returns at once because the process has no native Sentry export (the
"Sentry GDExtension not loaded in this process; skipping" line on stderr of every start).

This file lists **every** intervention of the integrated host: every Harmony patch and every call of a game test hook
or private / public setter that changes how the game behaves headlessly. It is ONE ledger for all modules; the six
team fragments `host\FIDELITY.<team>.md` are kept for history and marked as merged.

**How it is kept true.** Every intervention goes through `SpireHost.Core\Patches\PatchRegistry.cs` (fail-closed: a
missing target or a duplicate id throws at start; one patch per site unless the ids are declared together, section 3).
The tables of sections 1 and 2 are generated from the registry (`bench\h5\tools\gen_ledger.py`, the H1 generator plus the multi-seat rows) and
checked mechanically against it by the executable itself:

* `SpireHost --check-ledger` / `SpireHost --list-patches` - every id of the production set has exactly one row in
  section 1 with the same category and kind, there is no row without a registry id, and the rows of a shared site name
  each other (`SpireHost.Core\Patches\PatchLedger.cs`); exit 4 otherwise.
* `--patch-report FILE` on any command - the same check after the command ran, including the tool-only
  instrumentation that command installed (section 2).
* Phase H5 (2-4 seats in one process): section 11 states what the multi-seat host adds, what it sends for a remote
  seat and where, and what could not be compared with a real client.
* `fidelity --selftest` (`ledger_matches_registry`, `other_modules_fidelity_patches_name_a_selfcheck`) and
  `replay --selftest` (`ledger_lists_tool_instrumentation`) repeat it; `make-dist` refuses to write a manifest for a
  build whose ledger does not match.

Row format of sections 1 and 2: `id` | category | kind | target | what / why (the text the code registers; source
references are `ref\sts2-v0113-src` paths without the `MegaCrit.Sts2.Core.` prefix) | self-check.

Categories

* **Plumbing** - replaces an engine / UI / platform / IO call that cannot run without Godot, or blocks an outbound
  network call. Must not change game state or RNG consumption.
* **Scheduling** - maps a scheduling primitive (timer, deferred call, scheduler-less continuation, a save that
  completes synchronously only because nothing is written) onto the single-threaded pump. Must not change the logical
  order of events the real client can produce.
* **Instrumentation** - read-only: counters, captures, assertions that abort the episode.
* **Fidelity** - restores the REAL-game branch of a TestMode / NonInteractive / UI-node gate (the host must run with
  TestMode on). Each has: site (file:line), what the real branch does, how it is patched, a self-check (section 7).
* **Behaviour** - changes what game code computes. **The production set contains none** (checked at every start by
  `ProductionHost.Verify`, by `--list-patches` and by the gates).

**The production set: 114 registry entries** - Plumbing 37, Scheduling 8, Instrumentation 47, Fidelity 22, **Behaviour 0**. It is the same in every mode of the executable (serve, fuzz, determinism, replay-run, replay-mcr, compare-run-traces, every self-test): one module set, defined in `host\SpireHost\ProductionHost.cs`. Patch hash (`PatchLedger.Hash`, sha256 over the `id|target|kind|category` lines sorted by id): `b8da5999699f69bc9ef3f3727d75d453824940b35e221f28f5448989f7e8f821`.

The observation module (`obs`) installs no patch: the encoder only reads decision contexts and white-listed public game members at quiescent decision points (section 8 lists the game methods it calls that write state, and how each is undone).

## 8. The observation encoder: game methods it calls that write state, and computations that reproduce a game method

The encoder installs no patch. It runs at quiescent decision points (and at the terminal state) on the engine thread
and reads Decision contexts plus white-listed public game members (ruling D6; IL audit: `obs --selftest` case `audit`).
Each call below that writes state is undone before the encoder returns; the proof is the "no side effects" check of
`obs --selftest` (cases `fuzz`, `scenarios`, `real_special`: a deep state signature before / after every encode of
every decision, and a byte-identical second encode).

## 11. Multi-seat runs (phase H5): 2-4 seats in one process

A run with one seat is unchanged (`RunManager.SetUpNewSingleplayer`, the game's `NetSingleplayerGameService`; every
row of this section is inert). A run with 2-4 seats is set up with the game's own
`RunManager.SetUpTest(run, service, disableCombatStateSync: false)` + `GenerateRooms()` on the host's
`HeadlessHostNetService`: an `INetGameService` of type **Host** with no transport (host -> client messages are counted
and dropped, nothing is looped back, nothing leaves the process). The game's "fake multiplayer" (several players on a

Multiplayer.Game/TreasureRoomRelicSynchronizer.cs:114-125) is never used; `FidelityInvariants` asserts the service
type, the lobby, the enabled combat-state sync, the local player and "no run modifier" at every run start.

remote players: the host's simulation computes everything for them, exactly as on a real host, and each has a

holds the same state - with that seat's net id as sender, through the handlers the game registered. No message type

**Order of decisions** (one controller; DRIVER-API.md section 12). (1) pending frames, last in first out, for every
seat; (2) the top reward screen of the lowest remote seat that has one; (3) in combat, one decision that is the union

anything else to do, lowest seat first; with the option `team_votes` they are asked once and cast for every other
seat as that seat's own message. The treasure relic vote is per seat (the seats vote for different relics). Nothing
to ask is the stall `all_seats_waiting`.

aimed at an ally never targets its owner; no SKIP in the treasure room (Nodes.Rooms/NTreasureRoom.cs:158, :241-245);
an event option that would kill is not clickable (Nodes.Events/NEventOptionButton.cs:266-284) - which also keeps

reach, asserted; MEND exists (Entities.RestSite/RestSiteOption.cs:56-59).

**Harmony patch order** (found in this phase). A patched method's replacement is compiled when it is patched; a
small callee that is patched LATER is inlined into it and its patch never runs on that path. The capture of
`CardSelectCmd.FromDeckGeneric` is therefore installed before the one of `FromDeckForRemoval` (which calls it), and
`RemoteSeatPatches` before every module. The rebuild cross-check above would report a recurrence at the first prompt.

**Verification modes**: `--wire` (every client message is serialised and deserialised with the game's packet code
before the host handles it; an episode must be identical with it on and off) and the `--selftest-mp` cases named in
the rows of section 1.

**Real multi-client recordings** (`..\notes\oracle-mp.md`, `..\notes\host-h5-4p.md` section 2.5). The fights of real
2-4 player sessions are re-executed by `--replay-mcr --runs-mp` with the game's own multi-player replay sequence and
every recorded per-action combat state is compared: this checks the engine under this patch set with several players,
not the Host-type service or the virtual clients above. What the real clients sent (message types, requested actions,
their order per sender) was measured on the recorded host streams and agrees with the table above
(`bench\h5\tools\mp_stream_facts.py`). A real session replayed THROUGH the host path is the open item.
